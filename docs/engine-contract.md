# SatQuery Engine V1 — Public Contract

This document defines the stable, public interface between the SatQuery Engine and the backend service.

## 1. Engine Entrypoint

The backend interacts with the engine exclusively through the `SatQueryEngine` class.

```python
from engine.core import SatQueryEngine
from engine.contracts import InputBundle, ImageAsset

engine = SatQueryEngine()

result = engine.analyze(
    inputs=input_bundle,
    query="Are there any new buildings?"
)
```

The engine internally handles:
- Model selection and routing
- Lazy loading of heavy models
- Preprocessing and registration
- Hardware fallback mechanisms
- Evidence generation

The backend MUST NOT directly instantiate specialists or models.

## 2. Input Specifications

### ImageAsset
Represents a single remote sensing image.

Required fields:
- `id` (str): Unique identifier
- `path` (str): Absolute or relative filesystem path
- `filename` (str): Original filename
- `format` (str): E.g., "GeoTIFF"
- `modality` (str): "optical", "sar", or "multispectral"

Optional fields:
- `width`, `height`, `bands`, `crs`, `resolution`, `acquisition_time`, `bbox`, `metadata`

### InputBundle
A collection of `ImageAsset`s.

Supported combinations:
- 1 Optical Image -> `SINGLE_OPTICAL`
- 1 SAR Image -> `SINGLE_SAR`
- 2 Optical Images -> `TEMPORAL_OPTICAL` (Chronological ordering is handled by the engine)
- 2 SAR Images -> `TEMPORAL_SAR`
- 1 Optical + 1 SAR -> `OPTICAL_SAR_PAIR`

## 3. Output Specifications

The `analyze()` method guarantees it will return an `EngineResult` object. No raw exceptions are thrown to the backend.

### EngineResult

Guaranteed fields:
- `request_id` (str): Unique execution ID
- `status` (str): "success" or "error"
- `query` (str): The original query
- `task` (TaskType | None): The determined analytical task
- `answer` (Any): The final semantic answer (string, bool, int, or dict)
- `confidence` (float | None): Confidence score (0.0 to 1.0) if scientifically valid. Will be `None` for deterministic fallbacks.
- `specialist_results` (List[SpecialistResult]): Detailed outputs from each specialist tool invoked.
- `evidence` (List[EvidenceBundle]): Ordered list of evidence artifacts supporting the final answer.
- `execution_trace` (List[Dict]): Developer-oriented timeline of internal engine steps.
- `errors` (List[EngineError]): Structured error information if `status == "error"`.

### EvidenceBundle

Guaranteed fields:
- `textual_evidence` (str | None): A semantic explanation of the result.
- `bounding_boxes` (List[BoundingBox]): A list of located features.
- `visualizations` (List[str]): Paths to generated visualization masks/charts.
- `change_statistics` (Dict | None): Temporal metrics.
- `change_mask` (ChangeMask | None): Geospatial change artifact.
- `metadata` (Dict): Additional provenance.

## 4. Fallback Observability

If a heavy ML model fails to load or lacks hardware support, the engine automatically falls back to a deterministic baseline.

When a fallback occurs:
1. The engine completes successfully (`status == "success"`).
2. The `answer` is generated by the deterministic baseline.
3. The `confidence` is strictly set to `None`.
4. The `EvidenceBundle` metadata contains:
   - `fallback_triggered: True`
   - `fallback_reason: "<Reason>"`

The backend MUST NOT present fallback answers as AI-generated, nor attach fabricated confidence scores.

## 5. Error Taxonomy

If the engine fails to produce a result, `status == "error"` and the `errors` list contains an `EngineError` with one of the following codes:

| Error Code | Description |
|---|---|
| `INVALID_INPUT` | InputBundle violates schema or modality requirements |
| `INCOMPATIBLE_PAIR` | Images cannot be compared/registered (e.g. widely different geography) |
| `REGISTRATION_FAILED` | Geospatial alignment failed |
| `NO_COMPATIBLE_SPECIALIST` | No specialist supports the requested query+input combination |
| `PLANNING_FAILED` | Internal planner could not resolve a workflow |
| `ENGINE_TIMEOUT` | Execution exceeded safe time limits |
| `INTERNAL_ENGINE_ERROR` | An unhandled exception occurred |

*Note: Model failures (e.g., OOM) are caught by the engine and routed to fallbacks where possible, or converted to structured errors if no fallback exists.*

## 6. Execution Mode

The environment variable `SATQUERY_MODEL_MODE` controls the registry:
- `real`: Will attempt to load actual ML models (e.g., GeoChat, CROMA)
- `mock`: Uses stub implementations for immediate CI/Testing feedback

*(Default is `mock` if unspecified)*
